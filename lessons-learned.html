FELIX'S SNAKE CUBES — LESSONS LEARNED

Accumulated from the v3.0.x refactor session. Updated as the project evolves.

1. SCRIPT LOAD ORDER IS EVERYTHING

All JS files share a single global scope via plain <script> tags — NOT ES modules. This means:

  • Files must be loaded in dependency order (config → render → game-core → input → weapons → athena → multiplayer → settings → main)
  • A function defined in file N can be referenced in file M (M < N) only inside another function body — not at the top level
  • Top-level code in a file runs immediately when the script tag is parsed
BUG CAUGHT: requestAnimationFrame(loop) was placed in settings.js, which loads before main.js defines loop(). This throws a ReferenceError.
FIX: Always put the rAF kickoff at the very end of main.js, after loop() is defined.

2. DOM REFERENCES IN TOP-LEVEL SCRIPT CODE

settings.js grabs DOM elements at the top level (outside any function):

const _settingsBtn = document.getElementById('settings-btn');

This is fine only because all <script> tags are at the bottom of <body>, after all HTML is parsed. If scripts were in <head>, this would return null.

Rule: keep all script tags at the bottom of body, after all HTML.

3. ATHENA GUARD PATTERN

athena.js loads 6th. Files 1–5 (config, render, game-core, input, weapons) must not assume ATHENA exists at parse time. Use:

if (typeof ATHENA !== 'undefined' && ATHENA.active) { … }

Plain ATHENA.active in an early-loaded file causes ReferenceError if that code path runs before athena.js is parsed.

4. PLAYER_START_VAL TOUCHES MORE THAN ONE PLACE

To make everyone start at a given value, three things must all use it — missing any one breaks the intent:

  • newSnake() — the isPlayer branch used to hardcode val:2; must use val:startVal
  • initGame() player call — pass CFG.PLAYER_START_VAL || 2 as the startVal argument
  • initGame() initial bot loop — same value, so bots match the player's starting level
  • _worldMax init — must seed to CFG.PLAYER_START_VAL so food size scaling is correct from frame one
GOTCHA: _worldMax = 2 at the start of initGame() means all food spawns as tiny pellets even if the player starts at 1024. Food value floor = worldMax / 64, so seeding _worldMax correctly is critical.

5. THE MERGE SYSTEM REQUIRES POWERS OF 2

Segments merge when two equal values meet, doubling: 2+2→4, 512+512→1024. The entire value chain is powers of 2. Non-power-of-2 values (e.g. 6, 10, 14) never cleanly merge and produce odd leaderboard numbers.

RULE: Any config value that feeds into a segment's val must be a power of 2. Sliders for such values should snap to powers of 2.

// Map a linear slider (exponent 1–11) to powers of 2
function applyStartValSlider(exp) {
  CFG.PLAYER_START_VAL = Math.pow(2, exp); // 2, 4, 8 … 2048
}

6. SLIDER RANGE ENCODING STRATEGY

Two patterns used in this project:

  • Linear value: min/max/step match actual values (tick speed, bot count, etc.)
  • Exponential value: slider stores an exponent; JS converts to actual value. Use this for any value that grows multiplicatively (start val, difficulty multipliers).

Always add a --pct CSS variable so the slider fill gradient tracks correctly:

slider.style.setProperty('--pct', pct + '%');

7. MONOLITHIC FILE vs SPLIT FILES

The project maintains both:

  • Split files (index.html + js/ + css/) — the working/editing copy
  • Versioned snapshots (snake2048_vX.Y.Z.html) — single self-contained files for sharing/archiving

Changes must be applied to both. See process.html for the workflow.

8. SPAWNED BOTS vs INITIAL BOTS

Initial bots (created in initGame()) use a hardcoded startVal — this is where PLAYER_START_VAL needed to be threaded through.

Bots spawned later via spawnBot() already scale to playerHeadVal × CFG.DIFFICULTY — no change needed there.

9. FOOD SCALING IS DYNAMIC

spawnFood() computes a minimum food value as worldMax / 64. This means:

  • If you start at 1024, minimum food = 16 (not 2)
  • Food always stays somewhat relevant relative to the world's largest snake
  • Stale low-value food on the field gets upgraded: if(f.val < loFood) f.val = loFood

11. SLIDER INIT MUST READ FROM CFG, NOT OVERWRITE IT

Every slider calls an applyXxxSlider(value) function that writes into CFG. The natural pattern is to call that same function at page load to set a startup default — but this overwrites whatever config.js already set.

BUG: applyStartValSlider(1) at page load set CFG.PLAYER_START_VAL = 2, silently overwriting any value set in config.js. Setting PLAYER_START_VAL: 1024 in config had no effect because settings.js ran after config.js and reset it.

RULE: Slider init should sync the slider UI to the CFG value, not push a hardcoded default into CFG. Pattern:

// WRONG — overwrites config.js
applyStartValSlider(1);

// CORRECT — reads CFG, syncs slider to match
const _initExp = Math.max(1, Math.min(11, Math.round(Math.log2(Math.max(2, CFG.PLAYER_START_VAL || 2)))));
applyStartValSlider(_initExp);

Apply this pattern to any slider whose backing CFG value might be intentionally set in config.js. Sliders for purely runtime values (camera, bot speed) are fine to init with a hardcoded default.

Dev sliders modify CFG properties live (e.g. CFG.TICK_MS = v). This works because CFG is declared const (the binding is constant, not the contents). Some properties (like NUM_BOTS) are computed once at parse time from WORLD_DENSITY — changing WORLD_DENSITY later does NOT recompute these. Those need manual recalculation in their slider handler.

12. DOM INJECTION KEEPS index.html SLIM

Complex HTML (settings panel, MP overlay, joystick) was hardcoded in index.html, making it 300+ lines and defeating the purpose of splitting files. The fix: each JS file creates its own DOM elements via an IIFE at the top of the file, and index.html stays a ~70-line skeleton.

// At the top of settings.js — runs immediately when the script is parsed
(function() {
  const el = document.createElement('div');
  el.id = 'settings-panel';
  el.innerHTML = `... all slider HTML ...`;
  document.body.appendChild(el);
})();

// Then the rest of settings.js can safely do:
const _settingsPanel = document.getElementById('settings-panel'); // exists!
ORDERING: The build IIFE must run BEFORE any top-level const x = document.getElementById('...') that references the generated element. Since all scripts are at the bottom of <body> and run in order, putting the IIFE at the very top of the file guarantees the element exists when the rest of the file's top-level code runs.

For the monolithic snapshot, all three IIFEs are merged into one at the very top of the <script> block — before the TWEAK ZONE — so they run first.

Elements referenced only inside function bodies (like joy-zone in initJoystickHandlers()) don't have this constraint: they just need to exist by the time the function is called, not when the file is parsed.

14. TERRAIN-CONFORMING CUBES — LINEAR PLANE + SURFACE NORMAL

To make snake cubes tilt with rolling terrain without distorting their shape, cubeWorldPts() uses a two-step approach:

Step 1 — Bottom ring: locally-flat terrain plane

Compute the terrain height and gradient at the cube's centre only, then extrapolate a flat plane for all 4 corners. This keeps the bottom face coplanar (no 2D shear):

const h0 = terrainH(cx, cz);
const sx = terrainH(cx + 0.5, cz) - terrainH(cx - 0.5, cz); // dH/dX
const sz = terrainH(cx, cz + 0.5) - terrainH(cx, cz - 0.5); // dH/dZ
const bot = corners.map(c => ({
  wx: c.wx,
  wy: h0 + (c.wx - cx) * sx + (c.wz - cz) * sz,  // tangent plane
  wz: c.wz,
}));

Step 2 — Top ring: offset along surface normal

The cube's height direction is the terrain surface normal N = normalize(-sx, 1, -sz). Each top corner is the matching bottom corner shifted by h along N:

const nLen = Math.sqrt(sx*sx + 1 + sz*sz);
const top = bot.map(b => ({
  wx: b.wx - (sx / nLen) * h,
  wy: b.wy + h / nLen,
  wz: b.wz - (sz / nLen) * h,
}));

Result: all 6 faces are flat parallelograms. In non-Athena mode, terrainH=0 everywhere → sx=sz=0, nLen=1 → identical to the original flat-ground cube.

WRONG APPROACH: Sampling terrainH() at each of the 4 world-space corners individually produces a non-planar bottom face (the 4 points don't sit on the same plane when terrain curves). This makes the side faces into warped quadrilaterals — visually a 2D shear/parallelogram effect, not a 3D tilt. Never use per-corner terrainH for cube vertices.
CAMERA DISTORTION: At low camera heights (≤8), even correct terrain tilt causes large perspective swings. Two mitigations:
  • Raise the default CAM.height (8 → 14) — reduces angular movement for the same vertical displacement.
  • Dampen camera terrain-follow: camGroundY = terrainH * 0.4 with a slow lerp (0.08) so the camera slides through dips rather than snapping to them.

Face features (eyes, mouth) in drawHead still use the centre terrain height (terrainH(col, row)) as their Y base — sampling per-feature would cause jitter.

15. TOP-LEVEL DEAD CODE SILENTLY KILLS A WHOLE SCRIPT

Any top-level reference to an undefined name throws a ReferenceError immediately when the browser parses the script tag. Everything after that line in the same file is never executed — no error panel, no fallback, just silent failure.

BUG CAUGHT: multiplayer.js had dead code left at the top level from a refactor: 
const _origDraw = draw;   // draw is defined in main.js — loads AFTER multiplayer.js
const _origLoop = loop;   // same — throws ReferenceError here
This threw ReferenceError: draw is not defined, killing the rest of multiplayer.js — including the _startApp() that registers the MP overlay and audio. Result: MP overlay never showed, buttons dead, audio broken. The error was masked because the runtime error handler was also dead (hadn't registered yet).

RULE: Top-level code in file M must only reference names defined in files 1 … M-1 (already parsed). Names in later files (M+1 …) can only be referenced inside function bodies — they are resolved at call time, not parse time.

Always grep for top-level references to late-defined globals after any refactor. An unused const _x = globalFromLaterFile is a parse-time bomb.

13. window.load TIMING ON file:// PROTOCOL

When the game runs via file://, all scripts load from disk instantly — there is no network latency. This can cause a subtle ordering problem in split-file builds where scripts are at the very end of <body>:

  • In a monolith, the browser has more body HTML after the <script> block to process before firing window.load.
  • In a split-file build with scripts at the very end of <body>, after the last </script> the browser may fire window.load before an earlier script's window.addEventListener('load', …) listener has had a chance to register.
BUG: multiplayer.js registered window.addEventListener('load', _startApp) at the end of the file. On file:// with scripts at the bottom of body, window.load sometimes fires before this listener was registered, so _startApp() never ran and the MP overlay never replaced the old start screen.

FIX: Guard the listener registration with a readyState check:

function _startApp() {
  document.getElementById('s-start').classList.add('hidden');
  initMPOverlay();
}
if (document.readyState === 'complete') {
  _startApp();               // window.load already fired — call directly
} else {
  window.addEventListener('load', _startApp);
}

This pattern works on both file:// (where readyState may already be 'complete') and http:// (where it will be 'loading' or 'interactive' during script execution).

The ℹ diagnostic button in the HUD shows readyState captured at head-script time, DOMContentLoaded, and load — useful for confirming which branch actually ran.

17. BILLBOARD SPRITES ARE INHERENTLY TWO-SIDED; BOX FACES ARE NOT

Canvas 2D has no backface culling — every filled path is painted regardless of winding order. Despite this, hardcoded face-draw order on box-shaped objects (cup, dice, pencil) produces the wrong result when the camera is on the "wrong" side: the near face is painted first and then covered by the far face.

FIX: Collect all faces as data { pts, fill }, sort by average projected z depth descending (far first), then paint:

function _paintSorted(faces) {
  faces
    .map(f => ({ ...f, d: f.pts.reduce((s,p) => s+p.z, 0) / f.pts.length }))
    .sort((a,b) => b.d - a.d)
    .forEach(f => _face(f.pts, f.fill));
}

Also ensure all 6 faces of a box are present — the original code omitted the back faces, so the object was invisible from one side even though the missing faces would have been correctly sorted to draw-first.

Billboard shapes (screen-space circles, screen-space rectangles) are genuinely two-sided because they face the viewport by construction. Trees use this: trunk is a screen-space rect centred on the projected world position; canopy is a screen-space circle. No sorting needed for these — they always look correct.

18. PERSPECTIVE-CORRECT WORLD-TO-SCREEN SIZING USES _camF / depth

To draw a world-unit object (tree trunk width, canopy radius) at the correct screen size, use the focal length from render.js:

screenPixels = worldUnits * _camF / cameraDepth

_camF is updated each frame by _updateCamTrig() in render.js. cameraDepth is the .z field returned by project3(). This is exactly what the WebGL vertex shader uses — keeping the 2D canvas overlay in sync with the WebGL ground plane.

WRONG: Using a fixed heuristic like 120 / depth or Math.min(16, someConst / depth) breaks at different zoom levels and map scales. Use _camF for anything that must match world geometry.

19. ROAD / POLYLINE PROXIMITY CHECK — USE SEGMENT DISTANCE, NOT POINT DISTANCE

Roads in map-builder are stored as polylines (arrays of control points). Checking only those points for proximity misses the vast majority of the road — a long straight road with just two endpoints would only boost the player at the very ends.

The correct check is the minimum distance from the query point to each line segment in the polyline:

function _ptSegDist2(px, pz, ax, az, bx, bz) {
  const dx = bx-ax, dz = bz-az;
  const len2 = dx*dx + dz*dz;
  if (len2 < 1e-10) return (px-ax)**2 + (pz-az)**2;
  const t = Math.max(0, Math.min(1, ((px-ax)*dx + (pz-az)*dz) / len2));
  return (px-(ax+t*dx))**2 + (pz-(az+t*dz))**2;
}

Then compare _ptSegDist2(...) < threshold² (use squared distance to avoid a sqrt per segment). The threshold is (roadHalfWidth + CFG_DAD.ROAD_BOOST_OFFSET)² so narrower roads have a tighter boost zone.

This same pattern applies to any "near a path" query: hook range checks, road rendering, AI path following.

20. SPAWN FILTERING IN DAD'S MODE — CHECK ALL SPAWN SITES AGAINST _isWall

When Dad's mode is active, the collision grid (DAD._collGrid) marks every cell inside a building footprint. Any spawn function that picks a random cell must reject wall cells, or food and bots appear inside buildings.

Three places need the check — missing any one creates visible bugs:

  • spawnFood() — inner retry loop condition
  • randomFreeCell() — used by all specials (x2, boost, radar, invinc, vacuum)
  • initGame() initial bot placement loop — ring-spread positions can land in buildings

spawnBot() already had the check from the start. The player spawn had a spiral-out search from the map centre.

Pattern for any new spawn site:

if (typeof DAD !== 'undefined' && DAD.active && DAD._isWall(col, row)) continue; // or retry

21. DUPLICATE const ACROSS SPLIT FILES KILLS THE LATER SCRIPT SILENTLY

All JS files share a single global scope. Declaring const FOO = … in two different files is a SyntaxError: Identifier 'FOO' has already been declared — the entire second file stops executing at that line. Every symbol defined after the duplicate (including exported functions like startDad) is never created.

BUG CAUGHT: CFG_DAD was already declared in config.js (with CAR_PIXELS, SCALE, MAPS). Adding a second const CFG_DAD in dad.js threw a SyntaxError at that line, stopping dad.js before startDad was defined. The diagnostic panel reported "js/dad.js loaded but 'startDad' is not defined" — the correct signal.
FIX: Merge the new fields into the existing CFG_DAD in config.js and remove the duplicate declaration from dad.js.

RULE: Before adding any const / let / function declaration to a new file, grep all other JS files for that name first:

grep -r "const CFG_DAD" js/

The diagnostic panel's MISSING GLOBALS section is the fastest way to spot this: if a file loaded (FILES = ✓) but its key global is missing (GLOBALS = ✗), the cause is either a runtime error or a redeclaration SyntaxError early in the file.

Note: node --check file.js and new Function(src) both pass for this class of error because they only see one file at a time. The error only surfaces when both files are in the same scope (i.e., in the browser).

16. OVERLAY z-index BLOCKS HUD BUTTONS

Fullscreen overlays use position:fixed; inset:0; z-index:100. If #hud has no z-index it sits in the default stacking context (z-index: auto ≈ 0) — below the overlay — even though it is visually above it due to opacity and layout order. Clicks on HUD buttons pass through to the overlay behind.

BUG CAUGHT: After the MP overlay was shown, clicking the ⚙ and ℹ HUD buttons had no effect because the .ov overlay (z-index:100) captured all pointer events even though the HUD was visually in front of it.

FIX: Give #hud its own stacking context at a higher z-index:

/* styles.css */
#hud {
  position: relative;   /* creates stacking context */
  z-index: 150;         /* above overlays at z-index:100 */
}

Rule: any element that must be interactive above a fullscreen overlay needs position + a higher z-index than the overlay.
